# Постановка и координация

Следуй действующим системным, пользовательским и проектным правилам. Этот plugin
не устанавливает global bootstrap, модели, provider, права или лимиты.

1. Определи ожидаемый результат, разрешённые действия, точный cwd/scope и признак
   завершения по сообщению пользователя и текущим файлам. Проверка/объяснение сами
   по себе не разрешают правки. Уточняй только то, что существенно меняет результат.
2. Ограниченную самостоятельную задачу, включая исправление кода, решай прямо. Не создавай для
   неё контракт, run store или агентов. Для длительной или делегированной задачи составь короткий
   план с результатами, проверками и зависимостями.
3. Раздели содержательную работу на ближайшие законченные части. Если независимые
   части выигрывают от делегации и native tools доступны, назначь владельцев.
   Если tools недоступны, выполни части последовательно; текст роли не создаёт
   агента. Обычно достаточно 2–3 полезных потоков, включая ограничения основного
   чата. Root включается в cap только когда лимит runtime считает его. До spawn учитывай всех открытых потомков и idle threads в одном фактически
   доступном бюджете; не назначай потокам независимые квоты.
4. Каждый writer получает свою зону файлов, Git worktree от известной базы,
   критерии и команды проверки. Один writer на checkout; интегратор один.
   Сохраняй чужие изменения. Сохраняй текущие model/provider/permissions и учитывай defaults дочерних ролей; не меняй
   безопасность для удобства и не подставляй несуществующие названия моделей.
5. Длительную работу сохраняй в явно разрешённом приватном месте. Если установлен
   agent-harness, используй известные команды и `--help` при незнакомом интерфейсе. Для managed run подготовь контракт, вызови `init`, затем сохраняй `checkpoint`; Python не создаёт native агента. Если он отсутствует, достаточно разрешённого файла с goal/scope,
   owners, проверками и следующим шагом. Не устанавливай зависимости автоматически.
6. Исполнитель реализует и проверяет свой результат; основной чат рассматривает
   актуальный candidate. Ошибки возвращай прежнему владельцу с новой базой,
   failing check и evidence. Не повторяй действие с неизвестным исходом.
7. Перед утверждением об успехе сопоставь результат с критериями и свежими
   проверками именно этих входов. Отделяй NOT_RUN, skipped и unknown от passed. Для сохранённого accepted запроси `status --verify-evidence`, когда нужна текущая приёмка; обычный status её не доказывает. При failed compensation сохрани recovery receipt/journal и backups.
   Готовность владельца — ready_for_review, приёмка принадлежит основному чату.

Внешние записи, push/merge, сообщения и production требуют действующего основания
в задаче; зелёные проверки такого основания не создают. Ответь кратко: результат,
проверки, ограничения и оставшийся следующий шаг, если он нужен.
