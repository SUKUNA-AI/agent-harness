# Экономная организация работы

Выбранные модель/provider сохраняются; учитывай defaults и overrides ролей. Усилие координатора не меняй без
запроса. Механические подзадачи — medium; содержательная реализация и ревью —
high. Фиксированный effort native role TOML сильнее spawn effort; более высокое
усилие требует поддержанного пути и сложности/запроса. Не имитируй переключение.

Простую задачу выполни сам. Для полезной делегации обычно достаточно 2–3 потоков
в пределах более строгого project/runtime cap. Все потомки и idle/open агенты
учитываются вместе. Очередь логических направлений не требует одновременного spawn.
Раздели зоны записи; Git writer получает свой worktree. Общие generated outputs
пересобирает один интегратор. Чужие изменения не отменяй.

Общий контекст, решения и точный scope дай ссылкой на приватный run, не копируй
длинную историю каждому. Укажи нужные разделы больших файлов, входы, критерии,
checks и запреты. Финал агента — до 20–25 строк, подробности — в evidence.

Ищи `rg`, читай точечно, подсчёты и валидацию выполняй scripts. Объединяй
независимые чтения и безопасные проверки; неизменные инструкции не перечитывай. Большие PDF:
сначала структура/поиск инструментом, затем только нужные страницы. Долгую
команду запускай один раз и жди штатное событие без частого опроса. Проверяй
exit code, журнал и ожидаемые выходы. Не создавай задач ради ожидания.

Планируй ближайший этап или 2–4 недели. Остановись после приёмки. Повторяй
проверки только после релевантных изменений/сбоев. При длинном контексте сохрани
checkpoint/handoff с версиями, evidence и следующим шагом; приватную память
переноси лишь в явно разрешённую область. Новый контекст не называй native resume.

Сохраняй настроенный порог автосжатия 500000 и явные пользовательские overrides.
Уменьшение служебного текста измеряй в байтах; ускорение модели и экономию токенов
утверждай только по реальным сопоставимым запускам.
