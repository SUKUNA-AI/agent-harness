# Создание скиллов для harness

При оптимизации существующего поведения используй
`{{PACKAGE_ROOT}}/workflows/experiments.md`: фиксированный verifier, baseline,
отдельный holdout, ограниченный бюджет и наблюдаемый keep/discard. Не запускай
эксперимент перед каждой обычной правкой и не подменяй проверку большим prompt.

Выясни конкретный результат, примеры запросов и место установки из текущей задачи.
Если это уже ясно, приступай. Сначала проверь существующие skills: дублирование
общего harness и штатного `$skill-creator` обычно не требуется. При доступном
штатном creator используй его актуальные инструкции; этот skill самодостаточен.

Один skill — одна повторяемая процедура с различимым условием применения.
В `SKILL.md` обязателен YAML frontmatter `name` (имя папки, lowercase с дефисами,
до 64 символов) и короткий `description`: что делает и когда нужен. Ниже —
нужные решения и ограничения. Подробности выноси в связанные `references/`,
исполняемые повторяемые операции — в `scripts/`, реальные шаблоны — в `assets/`.
Не создавай пустые каталоги, незавершённые шаблоны, README и changelog внутри каждого skill.

Явные инструкции пользователя приоритетны. Skill не создаёт полномочий на push,
публикацию, отправку сообщений, смену прав или установку сервисов. Не добавляй
обязательный запрос подтверждения к уже разрешённой работе. Read-only запрос
сохраняет read-only scope. Не записывай секреты и чужой проектный контекст.

Зависимости должны быть необходимыми и проверяемыми. Предпочитай доступные tools;
если коннектор необязателен, опиши рабочий fallback. Укажи точные ограничения,
когда без него задача невыполнима. Подробности integrations — в
`{{PACKAGE_ROOT}}/integrations/README.md`. Автовыбор skill включён по умолчанию;
explicit-only устанавливается лишь по запросу пользователя.

Проверь YAML, относительные ссылки, отсутствие placeholders и противоречий.
Каждый новый script реально запусти на разрешённых изолированных входах.
Проверь 2–3 реалистичных запроса: целевой, похожий посторонний и с отсутствующей
необязательной интеграцией. Для сложного/рискованного skill полезно независимое
native ревью в общем бюджете. Структурный валидатор не доказывает поведение агента.

Для skill из этого пакета выбери имя с префиксом `harness-` и размещай в
`skills/<name>/`: installer ставит все его
файлы с подстановкой `{{PACKAGE_ROOT}}` и `{{MACHINE_POINTER}}`. Скрипты проверяй
в исходном дереве; не встраивай такие placeholders в исполняемый код. Для другого
skill используй выбранный пользователем location и доступный штатный validator.
