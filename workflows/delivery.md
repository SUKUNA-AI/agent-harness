# Реализация и исправление

Для web flow загрузи [браузерную приёмку](browser.md); для долгой работы —
[handoff и context](context.md). Required критерий остаётся not_run/failed, пока
нет актуального успешного наблюдения; skipped/notrun/suppressed не заменяют исполнение. Авторский самоотчёт не заменяет независимую проверку.
При новом уточнении пользователя сразу пересмотри цель, scope и ближайший шаг;
не продолжай устаревший план только ради завершения feature.

1. Установи разрешённую цель, актуальные инструкции, baseline и dirty/untracked состояние; сохрани чужие изменения без reset/stash/массового add.
2. Выбери прямой путь для ограниченной самостоятельной задачи: уточни scope/приёмку, внеси разрешённое изменение, выполни подходящие проверки. Для длительной, делегированной работы или восстановления через run создай сохраняемый контракт с digest: cwd, scope/protected objects, критерии и required checks. В shared YAML/документе разрешай конкретные records/области. JSON record scope сохраняет чужие значения и metadata с учётом типов: boolean отличается от number; custom format проверяет закреплённый adapter.
3. Ограниченную самостоятельную задачу выполняй прямо. Для полезных независимых частей подготовь plan/brief и автоматически назначь owners, обычно двух или трёх; при последовательной работе допустим один. Не создавай формальный план и дополнительных исполнителей только ради размера задачи. Сверь настоящий список threads и ledger; переиспользуй подходящие idle refs. Процесс и команды — [orchestration](../docs/ORCHESTRATION_RU.md), skill `harness-orchestrate`. Соблюдай общую ёмкость; один writer на checkout, свои worktrees и ветки от зафиксированной базы. Root единолично интегрирует, generated outputs и ресурсы сериализуются.
4. Исполнитель реализует, запускает подходящие проверки, диагностирует и исправляет в scope. При двух одинаковых провалах без новой гипотезы не повторяй вслепую. Делегированную ошибку возвращай прежнему owner с failing check/log/current candidate; для управляемого run создай новую attempt и безопасно обнови repair checkout.
5. Для управляемого run подготовь generated candidate, затем `freeze`, required `check` и содержательные/runtime/visual evidence. Нельзя менять candidate во время финального gate. `gate` root проверяет exact inputs/contract/attempt/evidence/scope и актуальное состояние, включая unknown operations; ready_for_review ещё не accepted. Уже принятые optional receipts также должны оставаться доступными и неизменными. При изменении state во время gate повтори приёмку по текущим условиям. При прямом выполнении достаточно обычных соразмерных проверок и их наблюдаемого результата; lifecycle commands/run-state не нужны.
6. Проверь взаимодействия и конечный пользовательский сценарий. После исправления повтори затронутые проверки и обязательные интеграционные gates. Для длительной работы сохрани checkpoint; сообщи результат и ограничения. Push/PR/merge/deploy требуют отдельного действующего основания.

Точные флаги и схемы — [CLI reference](../docs/CLI_REFERENCE_RU.md), ограничения evidence — [приёмка](../docs/ACCEPTANCE.md). Не дублируй managed lifecycle в простой прямой задаче.
