# Реализация и исправление

1. Установи разрешённую цель, актуальные инструкции, baseline и dirty/untracked состояние; сохрани чужие изменения без reset/stash/массового add.
2. Выбери прямой путь для ограниченной самостоятельной задачи: уточни scope/приёмку, внеси разрешённое изменение, выполни подходящие проверки. Для длительной, делегированной работы или восстановления через run создай сохраняемый контракт с digest: cwd, scope/protected objects, критерии и required checks. В shared YAML/документе разрешай конкретные records/области.
3. Ограниченную самостоятельную задачу выполняй прямо. Для полезных независимых частей подготовь plan/brief и автоматически назначь owners, обычно двух или трёх; при последовательной работе допустим один. Не создавай формальный план и дополнительных исполнителей только ради размера задачи. Сверь настоящий список threads и ledger; переиспользуй подходящие idle refs. Процесс и команды — `docs/ORCHESTRATION_RU.md`, skill `harness-orchestrate`. Соблюдай общую ёмкость; один writer на checkout, свои worktrees и ветки от зафиксированной базы. Root единолично интегрирует, generated outputs и ресурсы сериализуются.
4. Исполнитель реализует, запускает подходящие проверки, диагностирует и исправляет в scope. При двух одинаковых провалах без новой гипотезы не повторяй вслепую. Делегированную ошибку возвращай прежнему owner с failing check/log/current candidate; для управляемого run создай новую attempt и безопасно обнови repair checkout.
5. Для управляемого run подготовь generated candidate, затем `freeze`, required `check` и содержательные/runtime/visual evidence. Нельзя менять candidate во время финального gate. `gate` root проверяет exact inputs/contract/attempt/evidence/scope; ready_for_review ещё не accepted. При прямом выполнении достаточно обычных соразмерных проверок и их наблюдаемого результата; lifecycle commands/run-state не нужны.
6. Проверь взаимодействия и конечный пользовательский сценарий. После исправления повтори затронутые проверки и обязательные интеграционные gates. Для длительной работы сохрани checkpoint; сообщи результат и ограничения. Push/PR/merge/deploy требуют отдельного действующего основания.
