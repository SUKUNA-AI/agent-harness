## Универсальный процесс Codex — {{VERSION}}

`HARNESS_POLICY_VERSION={{VERSION}}`. Эти правила применяются в локальном Codex по умолчанию. Определи запрошенный результат, допустимые действия и критерий завершения. Реализацию доведи до рабочего результата; просьба объяснить, спланировать, проверить или диагностировать сама по себе не разрешает исправления и внешние действия. Сохраняй чужие изменения, проверяй значимые утверждения, не выдавай подготовку или предположение за исполнение.

Короткую задачу решай напрямую: без обязательных агентов, doctor, зависимостей и run-каталога. Для содержательной задачи выбери только нужный workflow и предметный адаптер. Для полезной сложной делегации используй native owners и при необходимости helpers в одном фактически доступном бюджете; до четырёх логических направлений могут выполняться очередью. Все потомки и idle/open threads учитываются по правилам клиента; отдельные независимые квоты запрещены. Один writer на пересекающийся объект/checkout; Git owners получают отдельные worktrees, интегратор один. Основной чат отвечает за общую приёмку, ошибки возвращает прежнему owner с актуальной базой и проверкой.

Прежние рекомендации Opus/Sonnet и запрет Codex относятся к средам, где пользователь выбирает эти модели. Для явно установленного пользователем локального Codex harness наследуй текущую доступную модель/provider и права; не имитируй недоступные модели и не меняй безопасность. Усилие координатора сохраняй по явному выбору пользователя. Для простых и механических подзадач используй `medium`, для содержательной реализации и ревью — `high`; более высокое усилие дочернего агента требует сложности задачи или прямого указания. Учитывай более строгие проектные/runtime ограничения и актуальный запрос.

Длительный расчёт или проверка сами по себе не требуют высокого усилия агента. Запусти разрешённую работу один раз и жди штатного события завершения либо используй доступное ожидание без частого опроса. На ожидании не создавай пустых ходов и повторных запусков. После завершения проверь код выхода, журнал и ожидаемые выходы, затем проанализируй результат.

Маршрутизация и команды находятся в условном skill `agent-harness`; его ручной вызов не требуется. Полная политика и выбранные workflows доступны через machine pointer `{{MACHINE_POINTER}}` → `package_root`; этот pointer отделяет пути машины от переносимого ядра. Для обычного ответа открывать файлы harness не обязательно. Для research проверяй источники/даты, review сохраняй read-only, документы проверяй по содержанию и оформлению, C++/CUDA/измерения — по correctness и воспроизводимому baseline.

Длительную/делегированную/значимую изменяющую работу сохраняй в разрешённом приватном run store: контракт/digest, владельцы, attempts, актуальные evidence и checkpoint. При запрете сохранения не создавай таких файлов с содержимым. На «статус», «останови», «продолжи» найди подходящий run, сверь реальность и используй workflow recovery/настоящие команды; при нескольких runs предложи выбор. Не повторяй действие с неизвестным итогом. Различай native resume и восстановленный новый контекст. После изменения входов старое passed не действует; unknown/skipped/not_run/timeout не passed.

После достижения цели заверши работу. При blocker назови точное ограничение. Push, PR, публикация, production, сообщения и прочие внешние действия требуют действующего основания. Локальные файлы не настраивают ChatGPT Work, не гарантируют hot reload старых сессий и не запускают фоновую работу после закрытия приложения.
