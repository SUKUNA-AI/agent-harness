# Исправления повторного аудита — 1.4.1

> Исторический отчёт указанной версии. Измерения и результаты ниже относятся
> к этому snapshot; актуальные команды — в [индексе документации](INDEX.md),
> текущая линия — [1.5.0](RELEASE_NOTES_1.5.0.md); результаты ниже не пересчитаны.

Область обновления — все 14 замечаний аудита версии 1.4.0. Приоритет: исключить
ложную приёмку результата, потерю пользовательских данных/метаданных и
неправильное связывание evidence с исходниками. Scanner и RepoMap остаются на
Rust, управляющий слой — на Python stdlib. Постоянных служб, БД и новых runtime
dependencies нет; настройки model/provider/reasoning/security и порог
`model_auto_compact_token_limit = 500000` не меняются.

## Проверяемые исправления

| ID | Исправленный контракт | Регрессионная проверка |
| --- | --- | --- |
| R01 | JSON boolean отличается от number, в том числе внутри dict/list; числовые 1 и 1.0 совместимы | Shared scope и JSON report не принимают подмену true/1 или false/0 |
| R02 | Обязательный GoogleTest case должен действительно выполняться | `notrun`, `suppressed`, skipped/disabled и неизвестные явные статусы не считаются passed |
| R03 | Command preflight, spawn и initial ledger относятся к текущему attempt и его workspace lease | Смена attempt перед запуском блокирует старую команду; смена workspace сериализуется |
| R04 | Install/rollback сохраняет поддерживаемые security metadata или отказывает до изменений | Настоящие Linux ACL/xattrs, staging failure, поздние metadata edits, install/reinstall/rollback и Windows DACL |
| R05 | Gate принимает только повторно сверенное состояние под state lock | Изменение ledger/unknown operations во время оценки отклоняет acceptance |
| R06 | Принятый набор receipts точно совпадает с текущим | Удалённый optional receipt делает accepted evidence устаревшим; изначально отсутствующий optional остаётся допустимым |
| R07 | Диапазоны навигации относятся к содержимому открытых снимков | Между первым ответом и capture меняется целевой файл; definition/references/symbols повторяются и возвращают согласованные ranges/SHA |
| R08 | `restored` означает проверенное восстановление из неизменного backup | Повреждение bytes, подмена inode/FIFO/symlink и правка после восстановления оставляют recovery state |
| R09 | Ограничение вывода не скрывает исход уже начатой транзакции | 1024-byte output сохраняет статус и receipt; слишком длинный recovery path отклоняется до source writes |
| R10 | Context packets и installation inputs читаются как bounded regular files | FIFO и regular→FIFO завершаются ошибкой без ожидания writer; symlink/reparse и чрезмерный размер отклоняются |
| R11 | Bundle содержит бинарник именно выполненной host-сборки | Реальный Cargo, установленный `CARGO_BUILD_TARGET` и старый flat artifact не приводят к упаковке устаревшего бинарника |
| R12 | Rust glob имеет ту же семантику, что Python fnmatch | Character classes, включая `[a--!a]`; изменение включённого файла меняет digest обоих backend |
| R13 | Git-root очищается только от разделителя записи Git | Root с конечным пробелом, tab или newline сохраняет Git inventory, missing tracked и ignore semantics |
| R14 | Неудачное восстановление bundle сохраняет прежние bytes и recovery path | Два отказа rename подряд не удаляют старый bundle при cleanup |

Регрессии используют временные изолированные каталоги. Они проверяют наблюдаемое
поведение; fault injection применяется к конкретным ошибкам записи и точкам
гонки. Позитивные сценарии — обычный JUnit, неизменный optional scope,
успешные install/rollback и rename — остаются частью общего suite.

## Установка и метаданные

Чтение установочных файлов ограничено 16 MiB на файл. Допустимы обычные файлы;
symlink/reparse, FIFO и меняющиеся во время чтения входы отвергаются. Ссылки
не нужно удалять ради установки: используйте обычные файлы либо отдельный
профиль с явно выбранными путями.

Windows CI выявил изменение bytes без наблюдаемого изменения timestamps.
Поэтому общий reader установочных файлов и packets на Windows дополнительно
сверяет содержимое вторым ограниченным чтением того же дескриптора, затем
проверяет тип и идентичность файла. Эта проверка не добавляет повторное чтение
в scanner/snapshot больших проектов.

На Linux установщик сохраняет mode, uid/gid и точный набор читаемых и
восстанавливаемых xattrs, включая POSIX ACL. Перед изменением любого target
проверяется возможность перенести metadata всех targets и active pointer.
Hardlinks, специальные inode flags, недоступные атрибуты, неподдерживаемая
платформа или ошибка staging приводят к отказу. Если metadata изменились во
время операции, они не считаются принадлежащими установщику; неподтверждённое
восстановление сохраняется как recovery state.

На Windows используются exact DACL staging/readback и `ReplaceFileW`, без
флагов игнорирования ACL errors. Проверяется owner/group; специальные attributes
и невозможность воспроизвести ownership отклоняются до замены. Это не обещание
поддержки всех security features любой сторонней файловой системы.

Rollback существующего файла сохраняет актуальную пользовательскую ACL. Для
удаления созданного установщиком файла требуется доказать, что пользователь
не изменил его metadata; недоказанное удаление отклоняется. Новые manifests и
journals содержат security metadata. Старые backups сохраняли только bytes и
не могут восстановить ACL, уже потерянные прежней версией.

## Проверки релиза

Обязательные команды и платформы заданы в
[workflow](../.github/workflows/check.yml). Python suite и MCP smoke выполняются
на Linux/Windows с Python 3.11 и 3.13; native jobs выполняют Rust tests, сборку,
scanner/RepoMap integration, реальные Cargo build/recovery регрессии и
LSP smoke с закреплённым Pyright. Release check проверяет версии, упаковку,
source/binary hashes, notices и исключение приватных файлов.

Локальные проверки не подменяют Windows CI. Для проверки конкретного ZIP
сверяйте `bin/<platform>/build-info.json`: version, source digest и binary SHA.
Сборщик явно передаёт `--target` для host, проверяет неизменность native sources
после Cargo и вычисляет binary hash уже на staged копии.

Независимый review выполняется по конечным diff и воспроизводимым сценариям,
а не только по числу зелёных тестов. В ходе него дополнительно проверяются
владение metadata после публикации, legacy manifests и сохранение прежнего
bundle при невозможности компенсации.

## Практические границы

Файловые locks координируют процессы harness, но не блокируют сторонний редактор.
При обнаруженной гонке сохраняется конфликт и recovery evidence. Это не общая
атомарная транзакция всей файловой системы и не отдельная OS sandbox.

LSP зависит от установленного language server и конфигурации проекта. Capture
и повторный запрос устраняют смешивание старого range с новым файлом; они не
доказывают полноту индекса самого сервера. Точный recovery receipt нельзя
заменять общим сообщением `ok`, даже ради экономии вывода.

Ускорение scanner/RepoMap из 1.4.0 сохранено. Это обновление исправляет
корректность и восстановление; отдельный новый процент ускорения не заявляется.
